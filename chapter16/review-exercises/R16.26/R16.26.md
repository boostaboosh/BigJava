Craig Coder doesn’t like the fact that he has to implement a hash function for the
objects that he wants to collect in a hash table. “Why not assign a unique ID to each
object?” he asks. What is wrong with his idea?

The problem with Craig’s idea is not assigning a unique ID to each object. That’s a good idea which is necessary for a hash table to work. Because each index in the backing array needs to correspond to a value which can be derived from the object stored there. In other words the index at which an object is stored in a hash table corresponds to the compressed unique identifier of an object. But what’s wrong with Craig’s idea is that he doesn’t realise that a hash function is (as best as possible) a unique identifier which can be derived from an object. If the unique identifier used to place the object in the backing array can’t be derived from the object itself then finding an object in the backing array will require iterating over positions in the array, leading to inefficient object retrieval. Adding objects would be inefficient too because you’d have to iterate over all elements in the backing array to add elements too. Because you’d need to ensure duplicates weren’t added to the hash table. But if the IDs objects are assigned are simply an incrementing integer counter for each new object, then two equal objects would receive two different IDs, so you can’t ensure that equal objects get the same ID. Instead you’d have to check all objects in the hash table for equality with the object you’re adding.
